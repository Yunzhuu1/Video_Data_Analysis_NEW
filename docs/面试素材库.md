# 面试素材库（项目一本通）

> 整合 `docs/简历素材.md` + `docs/源码阅读指南.md` + 底层设计问答 + 量化数据 + 演进点。
> 目标：每个底层设计被问到都能答得上来。配套源码阅读见 `docs/源码阅读指南.md`。

## 1. 项目定位（一句话）

构建了一个 **NL2DSL 的 ChatBI Agent**：用户自然语言 → LLM 语义解析为结构化意图（ResolvedIntent）→ **确定性合成器生成 SQL** → 统一门禁 → 执行 → 回答；配套语义记忆系统（命中直通/注入/表达映射）与**双闭环评测体系**（语义层 L1-L4 + 结果级 R1）。

## 2. 技术栈

Java 17 / Spring Boot 3（Spring AI）、Python 3 / LangGraph（StateGraph + checkpoint）、MySQL 8、DeepSeek（LLM）、火山方舟 doubao-embedding（2048 维）、LanceDB（HNSW cosine + ICU 中文 FTS）、OpenSpec 工作流。

## 3. 架构分层（面试必答）

**为什么 NL2DSL 而非 NL2SQL**：
- LLM 只输出结构化意图（intent/metrics/dimensions/time_range/filters/ordering），SQL 由确定性合成器产出
- 确定性：同意图同 SQL（可测可审计）；可控性：LLM 不接触 SQL 语法/表结构；可编排：记忆/门禁作用在意图层
- 长尾兜底：语义解析失败 → 降级 raw LLM SQL（fallback），但仍过门禁

**为什么 Java + Python 双栈**：
- Python（LangGraph）管编排（状态机/checkpoint/审批恢复）；Java（Spring）管平台治理（SQL 校验/执行/DQ/审计）
- 原则：**Python 不直连业务库**（执行必须走 Spring 统一安全入口）
- 解耦：LLM/编排演进不动平台层

**主链路**：ROUTER → SCHEMA → SEMANTIC_RESOLVE → SQL_SYNTHESIZE → SQL_HARD_GUARD → SQL_EXECUTE → SQL_SOFT_DQ → ANSWER；降级路径同样过门禁。

## 4. 底层设计问答（核心）

### 4.1 语义解析
- **LLM 怎么拿到指标名**：先由 `MetricCandidateRetriever` 做 schema linking（精确名称/code/最长别名 pinned + 字符 n-gram Top-5），再把候选指标字典注入 prompt；system prompt 只允许输出候选 metricCode，`response_format=json` 锁结构——**检索后约束生成**，不是全 catalog 自由猜
- **为什么暂时不用 embedding**：15 指标规模下，确定性词面召回已在 judged=49 上达到 `strict_recall@effective_k=49/49`，无需为技术栈完整性引入 API 成本；低信号自动回退 full，未来 catalog/跨语言表达扩大后再按同协议评估 embedding
- **pinned 为什么能超过 K**：显式命中优先于固定预算，`effective_k=max(configured_k,pinned_count)`；同时分别报告传统 `recall@configured_k` 与 pinned-aware `strict_recall@effective_k`，不偷换 Recall@K 概念
- **怎么保证输出可靠**：`_acceptable_intent`（metrics 非空 + intent 合法 + confidence≥0.5）→ 不满足走降级
- **golden_spec 同构**：ResolvedIntent 与评测 golden_spec 同构 → 比较器直接逐字段比，无需转换

### 4.2 确定性合成器（synthesize）
- **同意图同 SQL**：纯函数（无副作用/IO），单测直接验证
- **_resolve_path 动态路由**：同一指标不同问法走不同表（聚合→metric_daily 预聚合；排名→fact 数事件）——语义层与物理存储解耦
- **多指标为什么难**：①跨源（不同指标不同表）；②fact 各指标 eventFilter 不同会空结果；③约束只允许全 metric_daily 列路径 + aggregate/trend，其余显式降级（宁可不做不做错）
- **SUM 包裹**：metric_daily 行粒度 (date,category)，group by 粒度不同才 SUM（防重复求和）
- **失败路径**：SynthesisError → 节点 catch → semantic_ok=False → 降级 raw SQL

### 4.3 门禁/安全
- **三态裁决**：PASS / RETRYABLE（反馈重写）/ APPROVAL_NEEDED（审批）
- **两阶段**：静态语义层（jsqlparser AST：表-列注册、敏感列、意图-形态一致）→ 计划层（EXPLAIN：FACT 全扫→审批）
- **审批不变式**：门禁只跑一次；审批通过后执行/DQ 失败**不再重生 SQL**（防审批对象漂移）——thread_id=run_id + checkpoint 恢复

### 4.4 评测体系
- **L1-L4**：核心/严格/平均/分项（golden_spec 逐字段）
- **FakeLLM**：录制回放离线回归
- **R1 结果级**：独立手工 SQL 取 seed 42 确定性真值 + **真实 MySQL 审计执行**系统合成 SQL——**防自我确认**（系统不能验证自己）
- **失败分类**：sql_error/exec_error/value_mismatch；交叉诊断只统计 value_mismatch（"解析对但 SQL 错"信号）
- **评测驱动修复闭环**：R1 抓 c03"最近7天无时间过滤"真实 bug → 修复 → R1 12/12→17/17 验证

### 4.5 记忆系统
- **记什么**：norm_question → ResolvedIntent（只存 intent 不存 SQL）；写门槛 = 全链路成功
- **读取三分支**：hit（直通复用 + metrics 一致性校验）→ hit_rejected（校验不过，防毒化）→ inject（few-shot 注入，intent 去重 top-3）→ miss（LLM）
- **防误命中**：hit_allowed 四重判定（band + catalog + metrics 一致 + 可接受）
- **namespace 隔离**：eval vs default，评测不污染真实记忆
- **表达映射**：别名表（aliases.yaml 最长匹配）+ 指纹（MetricIdFingerprint embedding 候选）
- **真实路径**：real-session 协议（首问沉淀→二问命中→持久化验证），8/8

### 4.6 相对时间
- time_expand：relative → absolute（含端点，锚点=数据末日，seed 42 确定性）
- 锚点同源：_resolve_path 后 source 的 timeField（防漂移）

### 4.7 血缘感知查询规划（lineage-aware planning）
- **双 Agent 分工**：Semantic Agent 决定“查什么”；QueryPlannerAgent 只在系统枚举的合法候选中决定“怎么查”。LLM 可以权衡实时性与成本，但不能自造表、列、JOIN 或 SQL。
- **合法动作空间先于 Agent**：确定性 Enumerator 从指标 source 出发，只沿正向 N:1/1:1 边做最多两跳 BFS，候选上限 5；0/1/多候选分别走 legacy/AUTO_SINGLE/策略或 Planner。
- **选择路径就是执行路径**：CandidateQueryPlan 保存 GROUP_BY、FILTER、ORDERING、TIME_FILTER、TIME_BUCKET 的完整 fieldRoutes；Validator 与 Compiler 不允许重新 BFS，避免“规划选 A，执行偷偷走 B”。
- **可复现快照**：一次 run 冻结 lineage、metric definitions、schema projection；三份 canonical hash 合成 catalogVersion 并进入 planId，Java/Python 用固定 fixture 和仓库快照双重校验。
- **安全 JOIN 语义**：from 是指标行侧、to 是维度查找侧，只允许 from→to 的 N:1/1:1；反向和 fan-out 明确拒绝，而不是让 LLM 猜 cardinality。
- **灰度与回退**：`off|shadow|active`；shadow 只记录候选和验证结果但仍执行 legacy SQL，active 仅在 PASS 后走 plan compiler；多指标/detail/三跳/未知 binding 显式回退。
- **评测**：固定 intent 的 Path Recall 8/8、预期拒绝 2/2、非法计划拒绝 1/1、一次重选 1/1、代表性 MySQL EXPLAIN 4/4；active 真实 N=61 的 R1 仍为 29/29。
- **诚实边界**：这是 Git 版本化的单指标两跳 MVP，不是自动发现血缘、图数据库平台或生产级自进化优化器；真实 Planner 仅 N=2 方向性观测。

### 4.8 跨层对抗评测（adversarial-system-eval）
- **为什么不能只看准确率**：正常 golden 只能证明 happy path；对抗协议还要验证未知指标、prompt injection、非法 JOIN、候选篡改、快照漂移、审批对象漂移和故障恢复。
- **四层矩阵**：Semantic/Recall、Planning/Lineage、SQL Synthesis、Safety/Recovery 各 5 条，共 20 case；P05 三 variants 展开后为 22 execution units。
- **双状态**：Harness observation_status 回答“证据是否观察成功”，product disposition 回答“系统如何处置”；Harness PASS 不等于 System Readiness PASS。
- **崩溃可审计**：原子 journal + create-only terminal + lease/heartbeat + 幂等 finalizer；missing/duplicate/unknown/orphan 任一非零就拒绝聚合，防 runner 中断后静默缩分母。
- **防自我确认**：C01-C04 真值来自独立手工 SQL，不用被测合成器产出的 SQL 写 expected。
- **真实结果**：integrated Harness 20/20、P05 variants 3/3，但 Expected Disposition 12/20、R1 1/4、快照漂移 unsafe pass 3/3，所以 Readiness 明确为 FAIL。
- **诚实边界**：真实 LLM 仅 N=7 单轮方向性；这不是生产级红队认证，也不能声称 100% 安全。

## 6. STAR 故事（可整段讲）

- **STAR1 评测体系 + 驱动修复**：NL2DSL 缺可信评估 → golden_spec + L1-L4 + R1 → 端到端 47.6%→96%、R1 抓相对时间 bug 并修复
- **STAR2 语义记忆系统**：每问必调 LLM → 记忆命中直通/注入/表达映射 → 真实路径 8/8、token 省 21%、别名解锁
- **STAR3 产品能力补全**：多指标/相对时间缺失 → 同源多指标约束 + time_expand → n01 解锁、R1 12/12→17/17
- **STAR4 Schema linking 规模治理**：catalog 7→15 后全量 Prompt 变长并出现解析方差 → 设计 pinned-aware Top-5 + full fallback + 三口径召回门禁 → judged 49/49 覆盖、Prompt 字符 -53.16%、R1 29/29 不回退
- **STAR5 受约束 Agent 规划**：硬编码物理路由无法表达跨表路径，完全放权 LLM 又不可审计 → 枚举合法计划 + LLM 只选 ID + Validator/冻结快照/plan compiler → Path Recall 8/8、非法计划拒绝 100%、R1 29/29
- **STAR6 对抗评测与诚实交付**：happy-path 指标无法证明系统安全 → 20 case 跨层协议 + 双状态 + 独立 R1 + 原子 journal/finalizer → Harness 20/20 完整取证，同时定位快照漂移 unsafe pass 3/3 并如实判定 Readiness FAIL

## 7. 工程方法（体现素养）

- **渐进式变更**：20+ 独立 change（OpenSpec），每 change 独立分支 + 设计评审 + 评测回归 + 归档
- **评测驱动开发**：先建基线再开发；回归默认 --memory off（防记忆掩盖解析回归）
- **诚实方法论**：口径分离（场内自命中 vs 真实路径）、样本量卫生（N 标注）、防自我确认（R1 真值独立）、诚实报 0 增益
- **可复现**：seed 42 确定性 + 三变量标注（检索器/阈值/embedding）+ truth_source 审计
