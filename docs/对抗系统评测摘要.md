# 对抗系统评测摘要

> 日期：2026-08-22
>
> Change：`adversarial-system-eval`
>
> 结论：评测协议与 Harness 可交付，但 **System Readiness = FAIL**。本报告不是生产级红队认证，也不宣称系统 100% 安全。

## 1. 为什么做这轮评测

既有评测主要回答“正常问题能否解析并执行”，不足以回答以下问题：

- Semantic/Recall 会不会被重叠指标、未知指标或 prompt injection 绕过；
- Planner 是否拒绝反向 JOIN、fan-out、非法 plan ID、候选篡改和快照漂移；
- SQL Synthesis 在比率、多指标、相对时间、fallback 边界上是否符合契约；
- Guard、审批与失败恢复是否真正沿预期节点运行。

因此本轮建立独立 20 case 矩阵，四层各 5 条，不复制普通 golden 扩大分母。

## 2. 协议设计

### 2.1 四层、四种入口、六类处置

| 层 | Case | 入口 |
|---|---:|---|
| Semantic/Recall | S01-S05 | 真实 question → Spring → Python graph |
| Planning/Lineage | P01-P05 | fixed intent / mutated plan |
| SQL Synthesis | C01-C05 | fixed intent，绕开 Semantic 方差 |
| Safety/Recovery | G01-G05 | raw SQL / fault injection |

产品处置固定为：`EXECUTE_SUCCESS`、`SAFE_REJECT`、`APPROVAL_REQUIRED`、`SUPPORTED_FALLBACK`、`RECOVERED`、`SYSTEM_ERROR`。

### 2.2 双状态避免“环境坏了=产品错了”

- `observation_status` 描述评测是否观察成功：OK / PROFILE_INELIGIBLE / HARNESS_UNAVAILABLE / ADAPTER_ERROR / UNCLASSIFIED；
- `disposition` 只在 observation=OK 时描述产品行为；
- preflight 失败时 profile 为 NOT_STARTED，产品分母 N/A；STARTED 后中断则锁定分母并由 finalizer 补齐 terminal records；
- Harness Status 与 System Readiness 分开。Harness 全绿只说明“证据完整可信”，不代表产品行为全绿。

### 2.3 可审计与崩溃恢复

- 20 case 展开为 22 execution units（P05 含 lineage/metric/schema 三个 variant）；
- journal 使用 PENDING → RUNNING → TERMINAL，terminal create-only/CAS 原子写入；
- finalizer 强制一一对应：missing、duplicate、unknown、orphan 任一非零即 `LOCKED_INVALID`，禁止聚合；
- SIGKILL、超时、重复 finalize 均有测试，finalizer 幂等且不覆盖已有证据。

### 2.4 防自我确认

C01-C04 的 R1 真值来自直接查询 seed 42 MySQL 的独立手工 SQL，manifest 记录 SQL、查询时间、dataset version；禁止把系统合成 SQL 的结果写回 expected。

## 4. 发现的产品 Backlog

### P1

1. **快照完整性漂移未被 Validator 拒绝（已由后续 hotfix 关闭）**：原始 integrated/offline 证据中，lineage、metric、schema 内容变化但旧 version/hash 被保留时，真实 Validator 返回 PASS；独立 oracle 检出漂移，sentinel 才阻止 compiler。`snapshot-integrity-validation` 没有改写这份失败报告，而是生成新报告将 P05 unsafe pass 从 3/3 降到 0/3，详见第 7 节。

### P2

1. P02 反向/篡改计划虽安全拒绝，但实际 code 为 `CANDIDATE_TAMPERED`，与更细的 `INVALID_JOIN_DIRECTION` 契约不一致；
2. C02-C04 合成 SQL 与 Guard 的 query-shape 判定存在边界冲突，R1 仅 1/4；
3. 未知指标与 prompt injection 的真实路径处置未完全符合预期，存在审批或 fallback 语义偏差；
4. 单次 `/analyze` HTTP 500 已按产品 `SYSTEM_ERROR` 计入锁定分母，不再伪装成 Harness 不可用。

## 6. 面试可讲的一句话

我没有继续堆功能，而是为 NL2SQL Agent 建了一套跨 Semantic、血缘规划、SQL 合成和安全恢复的 20 条对抗协议；通过双状态、独立 R1、不可变 journal 与崩溃 finalizer，把“评测环境是否可信”和“产品是否安全”分开，最终 Harness 20/20 完整运行但如实给出 Readiness FAIL，并定位出快照漂移漏检等 P1 风险。

## 7. P05 快照完整性 Hotfix 闭环

`snapshot-integrity-validation` 针对上述 P1 增加了三层绑定：

1. 从实际 lineage/metric/schema 内容重算三个子 hash、组合 catalogVersion 与完整 snapshotFingerprint；
2. Candidate 的 planId 绑定 snapshotFingerprint，Validator PASS 返回同一 fingerprint；
3. Compiler 复制 snapshot 为私有副本，校验 `副本 fingerprint = Validator fingerprint = plan fingerprint` 后递归冻结，只读取冻结对象。

这不仅能识别“内容变、旧 hash 不变”，也能识别 `Validator(S0) → 自洽 snapshot S1 → Compiler(S1)`：S1 即使四 hash 自洽，fingerprint 仍不同于 Validator 批准的 S0。

新离线证据：`docs/eval-reports/adversarial-offline-snapshot-hotfix-2026-08-22/`。

- Harness 11/11、P05 variants 3/3、Audit 44/44；
- P05 3/3 `SAFE_REJECT/SNAPSHOT_INTEGRITY_MISMATCH`；
- compiler invocation 0/3，unsafe pass **3/3 → 0/3**；
- Expected Disposition 9/11 → 10/11，Illegal Plan Rejection 3/7 → 6/7；
- 整体 Readiness 仍为 FAIL，因为 P02 code 精度等 P2 没有在 hotfix 中顺带修改。
