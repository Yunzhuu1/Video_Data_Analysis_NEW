## [2026-08-13] BUG-003 修复（chartType 反序列化）+ 真实 LLM 首轮评测

**做了什么**：
- 修复 BUG-003：真实 LLM 生成的 charts 含 `chartType` 字段，Java `ChartConfig` DTO 只有 `type` 且未忽略未知字段 → `/api/agent/analyze` 500 `Unrecognized field "chartType"`。给 `ChartConfig`/`MetricPoint`/`DataPoint` 三个 DTO 加 `@JsonIgnoreProperties(ignoreUnknown = true)` 容错（保留 `type` 映射）。
- 单请求验证：原 500 的 c07（对比美食和游戏分类的播放趋势）现返回 HTTP 200，SQL/summary/charts 字段完整。
- `application.yml` 为所有必填占位符加默认值（DB `root/123456`、`AI_API_KEY:dummy` 等），支持 IDEA 一键启动；`AI_MODEL=deepseek-v4-flash`（用户手动指定，已保留）。
- 新增 `agent-engine/tests/conftest.py`：autouse fixture 强制 `eval_llm_mode=mock`，保证测试套件不因 `.env` 含真实 key 而发起真实 LLM 调用。

**Bug**：
- [BUG-003] 现象：LLM 输出 chart 含 `chartType` 字段 → Java 反序列化 500（`Unrecognized field`）。原因：`ChartConfig` DTO 仅声明 `type`，且无 `@JsonIgnoreProperties`。修复：3 个 DTO 加 `@JsonIgnoreProperties(ignoreUnknown = true)`。
- [BUG-004] 现象：`.env` 填入 `AI_API_KEY` 后 `pytest` 失败 1/57（`test_dq_warning_continues_to_answer`），warnings 多出 `Answer LLM fallback used: [Errno 8] nodename nor servname...`。原因：pydantic-settings 自动加载 `.env`，graph-flow 测试继承真实 key → AnswerAgent 在无网沙箱中真实调用失败 → 追加 fallback warning，破坏断言。修复：`tests/conftest.py` 强制 `eval_llm_mode="mock"`，`LLMClient.enabled()` 恒 False，恢复确定性 fallback。

**测试**：
- Python `pytest` 57/57、`ruff` clean；Java `mvn test` 14/14。
- 真实 LLM（deepseek-v4-flash）首轮 21 条评测（10:49）：评测可用性 71%（15/21）、端到端成功率 33.33%（5/15）、L1 口径核心 80%（8/10）、L2 严格 50%（5/10）、L3 平均字段 75%（judged=10）、L4 intent 80 / metrics 80 / dimensions 60 / time_range 80 / filters 80 / ordering 70；延迟 p50 43.4s / p95 97.8s（模型本身慢，单条 40–90s）。
- ⚠️ 该轮 6 个 ERROR（c07/c09/c12/c15/c16/c20）由 BUG-003 的 500 导致，修复后应计入 judged（L1 分母 10→13），需充值后重跑确认。

**结果**：
- 真实链路 500 根因（DTO 反序列化）已修复并单请求验证通过。
- 排查 `debug.resolvedIntent=null`：根因 = 语义解析的 LLM 调用失败（DeepSeek API 返回 **HTTP 402 Insufficient Balance**，账户欠费）→ 降级 fallback → `resolved_intent` 未写入。**非代码 bug，外部 API 欠费阻塞**。

**待办/下一步**：
- DeepSeek 账户充值后重跑 `cd agent-engine && .venv/bin/python -m app.eval.runner --llm real --platform real`（预计 10+ 分钟），验证 6 个 ERROR 恢复、L1 分母回到 13。
- 已知小缺口：`run_real_case` 未透传 `sql_source`，真实评测报告 Source 列恒为 `-`；后续可在 Python routes / Java debug 补透传。

## [2026-08-13] MySQL 真实环境联调 + 端到端评测

**做了什么**：
- 用户本机安装 MySQL 8.0.46（Homebrew），配置 `root/123456` + `video_data_analysis` 库。
- 启动 Spring Boot（`SPRING_PROFILES_ACTIVE=dev`）：自动执行 `schema.sql` + `DataInitializer` 种子数据（7 指标 / 12764 事实事件 / 3713 播放明细 / 93 聚合行）。

- 冒烟测试通过：Spring `/api/agent/analyze` → Python 引擎 → MySQL 真实 SQL 执行，全链路正常。
- 跑端到端评测 `--llm real --platform real`（21 条用例走真实平台）。

**Bug**：
- [BUG-001] `/internal/metrics` 返回 500：`MetricCatalogService.BASE_SQL` 的 SELECT 漏查 `fact_formula`/`fact_event_filter` 列，`map()` 读列时报 `Column 'fact_formula' not found`。→ 修复：SELECT 补上两列。（该 Bug 只有真连 MySQL 才会暴露，mock 模式跑不出来。）
- [BUG-002] eval runner `run_real_case` 两处：
  1. Spring 的 `debug.sqlRetryCount` 显式返回 `null` 时，`.get(key, default)` 不生效 → `int(None)` 崩溃，21/21 全 ERROR。
  2. Spring `/api/agent/analyze` 直接返回 `AnalysisReport`（无 `finalReport` 包装），runner 读报告字段全空。
  → 修复：`or 0` 兜底 + `or payload` 兜底。

**测试**：
- Python `pytest` 57/57、`ruff` clean、Java `mvn test` 14/14。
- 真实平台链路（fallback 模式，无 API key）：评测可用性 100%（21/21 无 ERROR）、端到端成功率 76.19%（16/21）、延迟 p50/p95 = 555ms/629ms。
- L1~L4 = 0%：无 API key 时语义解析不运行，属预期。

**结果**：
- MySQL 配置与真实平台链路完全验证通过；修复 2 个真实路径 Bug。
- 剩余 5 个失败均为无 API key 的预期行为：c15/c16/c17 依赖 mock 注入 guard/DQ 失败（仅 mock/replay 模式有意义）；c18/c19 需真实 LLM 生成高风险明细 SQL 才触发 HITL 审批。

**待办/下一步**：
- 在 `agent-engine/.env` 填入 DeepSeek `AI_API_KEY` 后重跑 `--llm real --platform real`，出真实 L1~L4 数字并验证 HITL/重试场景。
- 修复已提交到 `codex/eval-real-hotfix` 分支（含 `MetricCatalogService.java`、`runner.py`、`.gitignore`、`docs/开发日志.md`、`AGENTS.md` 日志规范）。
