# 记忆系统设计（思路记录 · 暂不实现）

> 状态：设计草案。本文件只记录思路与可行性判断，不进入当前开发主线。
> 关联现状：ChatBI 主链路已具备 SEMANTIC_RESOLVE（语义解析）+ 确定性 SQL 合成 + metric_definition 指标字典 + eval harness（golden cases + A/B compare）。

## 1. 背景与动机

当前 ChatBI 主链路：

```text
ROUTER
  -> SCHEMA
  -> SEMANTIC_RESOLVE
  -> SQL_SYNTHESIZE
  -> SQL_HARD_GUARD
  -> SQL_EXECUTE
  -> SQL_VALIDATE
  -> SQL_SOFT_DQ
  -> ANSWER
```

每次查询 LLM 都从零开始做语义解析，存在三个问题：

1. 重复问题反复消耗 token 与延迟，解析结果还可能漂移（同问不同答）。
2. 常用业务问法、指标别名、查询模式没有沉淀；换一种说法就可能解析失败或降级到 raw SQL。
3. 语义层只有指标口径（metric_definition），缺少"这个问题以前是怎么问的、怎么解析成功的"行为记忆。

## 2. 思路拆解：三件事，成熟度完全不同

原始想法："在用户多次查询时提炼出常用的查询模板或指标关系逻辑，让 LLM 生成 SQL 更快更准确。"

这句话实际混了三件成熟度不同的事，必须拆开判断：

| 子能力 | 内容 | 成熟度 | 业界参照 |
|---|---|---|---|
| 常用查询检索 | 相似问题 -> few-shot 示例注入 prompt | **高** | DAIL-SQL / AES-SQL（Text2SQL 评测均验证 few-shot 示例检索能显著提升准确率） |
| 查询模板提炼 | 从历史问答自动归纳"问法模板" | 中（AST 结构聚类后可再提升，见 §2.1） | 衡石科技、阿里 DataWorks 等落地做法基本是"人工审核 + 沉淀"；纯文本/embedding 聚类不可靠，但**带类型的 SQL AST 结构聚类**（字面量→槽位）是确定性的，可靠度显著更高 |
| 指标关系逻辑 | 指标口径、维度、粒度、血缘关系 | 不应从查询学习 | dbt MetricFlow / Looker LookML 都是**显式建模**，口径是业务权威定义 |

### 核心结论

**"指标关系逻辑"应该归语义层显式建模，而不是记忆系统。** 现有 `metric_definition` 表（指标口径/公式/维度/粒度/来源表/时间字段）就是这个方向的雏形，对标 dbt MetricFlow / LookML 的语义层。从查询行为"学"指标口径是危险的：口径是业务方定义的权威事实，不是从数据中统计出来的规律，自动提炼会产生看似合理实则错误的口径。

记忆系统只负责三类行为记忆：

1. **few-shot 示例**：question -> 成功的解析/合成路径（最成熟、最容易量化）。
2. **指标别名**：业务叫法 -> metric_code（用户习惯沉淀）。
3. **用户偏好**：默认时间粒度、常用维度、常用过滤条件。

## 2.1 带类型 AST：把"模板提炼"从文本聚类升级为结构聚类

原始判断"纯自动聚类不可靠"是基于文本/embedding 聚类；若引入带类型的 SQL 语法树（如 Apache Calcite 的 SqlNode），**结构是确定的，字面量是槽位**，模板提炼的可靠性完全不同。

```text
两条不同问法，同一结构:
  "美食类视频总播放量是多少"   vs   "统计游戏分类的播放量"
  → SEMANTIC_RESOLVE → 不同 intent（文字不同）
  → SQL_SYNTHESIZE   → SQL 不同（'美食' vs '游戏'）
  → Calcite 解析为 typed AST
  → 归一化（字面量→槽位）:
      SELECT category, SUM(total_plays) FROM metric_daily
      WHERE category IN (?, ?) GROUP BY category
  → 结构一致 → 归入同一模板
```

### AST 在记忆各环节的机会

| 环节 | 机制 | 说明 |
|---|---|---|
| 模板归一化/去重 | 字面量→槽位后同构 AST 合并，累计频次 | L2 沉淀的前置过滤 |
| 模板校验 | 槽位化骨架再过一遍 Calcite validate | 保证"带类型槽位"的模板本身合法 |
| few-shot 精确匹配 | 新问题→意图→合成→AST，与模板 AST 做结构相似度 | 比纯文本 embedding 更准（读取侧可选项） |
| 增量沉淀 | 高频 + eval 通过的结构才升 L2 | 复用 §6 验收闭环 |
| 评测金标准 | 从 AST 反推 golden_spec 结构维度 | eval harness 增强 |

### 小实验验证（2026-08-13，Calcite 1.37）

用当前 golden cases 的 13 条合成 SQL（`synthesize()` 产出）过 Calcite（MySQL 方言）归一化：字面量→`'?'` 槽位后按结构聚类。

**结果：**
- 13 条 SQL → **12 个结构模板**；其中 c03（最近7天）与 c13（最近一周）**自动合并**为同一模板（同构不同问法、同构不同时间量词）——正是 AST 结构聚类的价值。
- 若进一步把"指标名"也槽位化（`total_plays`/`total_likes`/`total_shares` 视为语义槽位而非结构），c01/c09、c02/c11 等会继续合并，模板数预计降到 6~8 个。

**暴露的两个集成注意点：**
1. **Calcite 保留字比 MySQL 严格**：`date` 等字段名/别名需反引号包裹（`md`.`date`）才能解析——真实接入时合成器应统一输出带反引号的标识符（本就是好实践）。
2. **Calcite unparse 产物与 MySQL 方言有细微差异**：如 `FROM metric_daily AS md`（显式 AS）、`BETWEEN ASYMMETRIC ? AND ?`（MySQL 无 ASYMMETRIC）——若模板要回填执行，需方言适配（如 `BETWEEN ? AND ?`）。

**结论**：AST 结构聚类可行且有效，可作为 L2 模板沉淀的前置过滤器；指标槽位化 + 方言适配是落地时的两个细化点。

### 关键边界（重要）

- **AST 是"写入侧/校验侧"的利器，不是"读取侧"的入口**：读取时（SEMANTIC_RESOLVE 之前）还没有 SQL，自然没有 AST；检索仍以问题 embedding + few-shot 打底，AST 用于沉淀、去重、校验、以及命中后的结构确认。两者互补。
- **AST 模板沉淀"问法结构"，不学"指标口径"**：口径/公式/粒度仍是 `metric_definition` 的权威定义，模板只引用它——与 §2"指标关系归语义层"的边界一致。
- **解析基础设施两处复用**：同一套 Calcite 解析同时服务 SQL_GATE（静态语义校验层）与记忆模板归一化。

## 3. 分层记忆设计

```text
┌──────────────────────────────────────────────────────┐
│ L3 语义层（显式建模 · 静态 · 权威）                   │
│   metric_definition：指标口径/公式/维度/粒度/来源表    │
│   已有实现，不属于记忆系统，记忆不得覆盖              │
├──────────────────────────────────────────────────────┤
│ L2 长期记忆（跨会话 · 动态 · 可增长）                 │
│   · few-shot 示例库：question -> 解析/合成路径         │
│   · 指标别名表：业务叫法 -> metric_code                │
│   · 用户偏好：默认粒度 / 常用维度 / 常用过滤          │
│   · 沉淀门槛：高频 且 eval 验证通过才写入             │
├──────────────────────────────────────────────────────┤
│ L1 短期记忆（会话内）                                │
│   · 上下文延续：上一轮 ResolvedIntent / SQL / 修正反馈 │
│   · 修正即信号：用户改了什么，就是 L2 的候选素材       │
└──────────────────────────────────────────────────────┘
```

### 写入路径（按成本递增，建议分阶段）

| 阶段 | 写入方式 | 质量保障 |
|---|---|---|
| 1 | 会话内自动写入（L1） | 仅限单次会话，风险低 |
| 2 | 高频 + eval 回归通过后自动沉淀（L2 few-shot） | 自动化兜底：golden cases 不回归 |
| 3 | 人工审核确认后发布（L2 权威模板） | 最强保障，成本最高，作为兜底通道 |

### 读取路径

在 SEMANTIC_RESOLVE 之前检索，把命中示例注入 prompt 作为 few-shot（DAIL-SQL 思路），**不是**让 LLM 依赖记忆直接输出 SQL。记忆只提供"这个意图以前怎么解析的"参考，最终仍走语义解析 + 确定性合成的确定性路径，避免记忆污染直接进 SQL。

## 4. 与现有系统的关系

- **SEMANTIC_RESOLVE（SemanticResolver）**：NL -> ResolvedIntent 的确定性入口。记忆系统在这里"加检索上下文"，而不是绕过它。
- **metric_definition（MetricCatalogService）**：指标关系逻辑的权威源，记忆系统不得覆盖。
- **LangGraph checkpoint（SqliteSaver）**：已具备会话级状态持久化，L1 短期记忆可直接承载，无需新存储。
- **eval harness**：见 §6，是记忆系统的验收工具。

## 5. 方案选型对比

| 方案 | 定位 | 适配度 | 结论 |
|---|---|---|---|
| **LangMem**（LangGraph 官方） | 记忆管理 SDK（memory manager / memory tool） | 高：本项目已用真 LangGraph | 长期记忆基础设施首选候选 |
| Mem0 | 跨会话长期记忆抽取（用户/会话粒度，~48k stars） | 中：偏通用对话，非 SQL 领域 | 借鉴其分层抽取与时效策略，不直接引入 |
| Zep / Letta | Agent 记忆层 | 中 | 参考 |
| DAIL-SQL / AES-SQL | Text2SQL few-shot 示例检索与评测 | 高：直接指导检索与评测范式 | 实现范式的参照 |
| dbt MetricFlow / LookML | 语义层显式建模 | 印证"指标关系归语义层" | 不做进记忆系统 |
| Apache Calcite | SQL 解析 + 类型化 AST + 语义校验 | 高：Java 栈，解析基础设施可与 SQL_GATE 复用 | 模板归一化/校验的底层依赖（可选先以 sqlglot 验证） |

### 5.1 成熟设计映射（2026-08 调研结论）

**直接回答"有没有适合本场景的成熟记忆系统"**：没有开箱即用的"ChatBI 语义记忆"产品，但有成熟范式/机制可以组装。本场景本质是 **example-based memory（示例记忆）+ 结构化写入 + 确定性读取**，业界最贴合且被验证的是 DAIL-SQL 系 Text2SQL few-shot 检索范式——**抄成熟机制，不抄框架**。

| 成熟设计 | 抄什么 | 不抄什么 | 对应本系统 |
|---|---|---|---|
| **DAIL-SQL**（Spider 72.3%→83.5%） | ①LLM 学的是 "question → 骨架" 映射（示例注入范式）②示例选择 = 问题相似 + SQL 骨架相似 | 它注入 SQL 示例；我们只注入 intent 示例 | few-shot 注入（已落地）；骨架相似度 → §2 AST 模板层（后续） |
| **CoALA**（普林斯顿，agent 记忆四型） | working/episodic/semantic/procedural 分型叙事 | 不作为技术规范 | 本系统 L1/L2/L3 分层可映射：L1=working、L2 few-shot=episodic、指标别名/偏好=semantic、SQL 模板=procedural |
| **LangMem**（LangGraph 官方） | 三型记忆 + 工具式读写 + consolidation/decay 思路 | Postgres/多用户/LLM 自由写入 | 写入走确定性钩子（全链路成功才沉淀），不引入 SDK |
| **Mem0** | **multi-signal 检索融合（语义+BM25+实体）** + 时效/衰减排序 | 抽取式事实记忆（LLM 抽用户事实） | **检索融合是本 change 的核心**；decay 用 hit_count/last_hit_at 手写 |
| **Zep / Graphiti** | -（时序知识图谱，为多轮实体关系演变设计） | 整个跳过 | - |
| **MemGPT / Letta** | -（OS 式分页，解决长上下文） | 整个跳过 | 上下文不大 |
| **Qdrant / pgvector** | hybrid search 是存储层标准形态 | 重依赖 | 存储选型见 §5.3：**定 LanceDB**（嵌入式 + 原生混合），Qdrant 为多实例迁移目标 |

### 5.2 检索层结论（本 change 的设计输入）

- **语义 + 关键词多信号融合**：语义向量为主（解决中文近义改写：播放量/观看量）——**embedding 来源选定为外接火山方舟 doubao-embedding API**（文本端点，零新增 pip 依赖、国内网络稳定、成本可忽略，调用失败降级 difflib）；BM25/词面信号为辅（保留精确词匹配，防纯向量漏词）；两块分数加权融合后走双阈值。
- **阈值重标定**：hit = 「毒化对全部落在 hit 之下」的最小值；inject = 「期望注入同义条目全部落在 inject 区间」的最大值（离线脚本产出分布，可复现）。
- **时效衰减**：hit_count / last_hit_at 作为排序权重（借鉴 Mem0/LangMem decay），随行存 LanceDB，检索后排序即可。
- **存储**：**LanceDB 本地目录**（`memory.lance/`，嵌入式列式 + HNSW/IVF-PQ + 原生 BM25 FTS + WAL），选型与代价见 §5.3。
- **降级保险**：embedding 模型不可用 → 自动降级 difflib（现状行为），不打断主链路。

**推荐路径**：few-shot 示例检索已落地（semantic-memory change）→ **下一步 = 语义+BM25 融合检索 + 阈值重标定 + 实验重跑**（独立 change：memory-hybrid-retrieval）→ 指标别名第三优先 → 模板自动提炼（AST 骨架相似度）与用户偏好最后做。

### 5.3 存储选型：LanceDB（2026-08 决策记录，面试叙事用）

**约束**（不是"谁最好"，而是"谁匹配"）：
1. **嵌入式/无服务端**：单节点 agent-engine，嵌入式消灭进程/网络/鉴权一整类故障面。
2. **Python-only**：记忆读写全链路在 Python agent-engine；Java 只透传 `memoryNamespace`（零改动）。
3. **原生混合检索**：语义（dense）+ 词面（BM25 FTS）+ 结构化过滤（namespace / metric_codes）一条查询——正是"多信号融合"设计的存储侧需求。
4. **规模路径**：不迁库的前提下 1k → 百万条。
5. **零运维、轻依赖、离线可用**。

**决策矩阵（约束 × 候选）**：

| 候选 | 嵌入式 | Python | 原生混合检索 | 持久化/过滤 | 规模路径 | 代价 |
|---|---|---:|---|---|---|---|
| **LanceDB** ✅ | ✅ | ✅ | ✅ 向量+BM25+过滤 | ✅ WAL/列式 | 同库 1k→1e8 | +pyarrow（几十 MB） |
| Qdrant | ❌ 服务端 | ✅ | ✅ 最强（dense+sparse） | ✅ | ✅ | 多一个 Rust 进程 |
| Milvus | ❌ 分布式重 | ✅ | ✅ | ✅ | ✅ | etcd/MinIO/消息队列，单节点过度工程 |
| Chroma | ✅ | ✅ | ⚠️ 弱 | ✅ | ⚠️ | 偏原型工具，性能/混合弱 |
| pgvector | ❌ 要 Postgres | ✅ | ⚠️ 只向量+SQL | ✅ | ✅ | 引入 DB 服务，与"Python 不碰业务库"原则冲突 |
| FAISS | ✅（纯库） | ✅ | ❌ | ❌ 无持久化 | 自建 | 只是索引库，等于重写一个向量库 |
| zvec | ✅ | ✅ | ✅ | ✅ | ✅ | v0.6 太新，API 演进风险 |

**为什么是 LanceDB（三个分水岭）**：
1. **嵌入式 vs 服务端**：Qdrant 是唯一真正接近的对手，但为单节点多养一个进程不值——嵌入式消灭整类故障面（进程管理/网络/鉴权）。
2. **原生混合检索是架构需求**：向量 + BM25 FTS + 结构化过滤一条查询，正好是"多信号融合"设计；Chroma 混合弱、FAISS 根本没有（它只是索引库，持久化/过滤/混合都要自建）。
3. **磁盘列式规模路径**：Lance 格式 + HNSW/IVF-PQ，同一个本地目录 1k→百万条不迁移——"不为今天的 100 条买集群，也不为明天的 100 万条换库"。

**诚实的代价（面试主动暴露）**：
- LanceDB **分布式/多节点能力不如 Milvus/Qdrant 成熟**（OSS 单节点定位）。
- 若产品**第一天就是多租户 SaaS / 需要共享存储** → 换 Qdrant（服务端、混合检索最成熟、可上分布式）。
- Chroma 更适合纯原型验证；本场景选它只会被当成 demo 货。

**迁移边界（把代价写进架构，而非祈祷不发生）**：
- `Retriever` / `VectorStore` 接口抽象：`nodes.py` 只依赖接口，不依赖具体实现。
- 换库 = 换一个 `VectorStore` 实现 + 数据导入；图/门禁/评测/Java 全不动。
- **触发条件明确**：多实例共享记忆 / 多租户隔离 / 需要分布式 → 迁移到 Qdrant。

## 6. 验收闭环（关键）

已有 eval harness 天然是记忆系统的验收工具：

```text
基线    ：当前无记忆的 eval 报告（docs/eval-report.md 已存在）
实验组  ：开启记忆检索后跑同一批 golden cases
A/B 对比：app.eval.runner --compare 对比 L1-L4 口径正确率
增量验证：追加"新问题" case，测冷启动 vs 热启动的收敛速度
```

度量指标：口径正确率（L1-L4）、SQL 可执行率、平均延迟、token 消耗。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 陈腐模板：沉淀的模板基于过期口径 | 每条记忆带来源/版本/失效机制（借鉴 schema 缓存 refresh）；eval 回归 |
| 时效性：记住的"答案"会过期 | few-shot 只提供生成策略，不提供结果；结果时效由 SQL 执行保证 |
| 口径漂移 | 记忆与 metric_definition 严格分离；口径变更走语义层，不走记忆 |
| 记忆污染：失败查询被沉淀 | 只有 eval 通过的才写入；阶段 3 人工审核兜底 |
| 多租户/隐私 | 用户级记忆隔离（当前单用户 demo 可延后） |

## 8. 结论

1. 思路总体可行，但必须拆开执行：**记忆系统聚焦 few-shot 示例检索 + 指标别名 + 用户偏好；指标关系留在语义层（metric_definition）。**
2. 最小可行版本 = few-shot 示例检索 + eval A/B 验收，工作量可控、价值可量化。
3. 模板提炼建议走 **AST 结构聚类**（Calcite/sqlglot 归一化，字面量→槽位），作为 L2 沉淀的前置过滤器；先跑小实验验证现有用例能聚出几类结构，再决定是否纳入主线。
3. 暂不实现。正式推进时建议作为独立 OpenSpec change，先做方案设计再进 tasks。
